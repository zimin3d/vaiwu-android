# План улучшений и стабилизации разработки

Составлен по итогам ревью `v0.1.1`/`v0.1.2`. Цель — не «добавить фич», а сделать так, чтобы существующие фичи нельзя было сломать незаметно.

Отдельный план по удобству и визуальной целостности интерфейса — `docs/ui-redesign-plan.md`.

## 1. Диагноз

За два релиза проект вырос из «одного экрана с питомцем» в приложение с экономикой, RPG, мини-играми, ассистентом, голосом, напоминаниями и автообновлением. Скорость роста обогнала инфраструктуру качества:

- ключевая механика (сон → болезнь → смерть) не покрыта ни одним тестом;
- UI и нативная модель расходятся, и это негде проверить;
- пользовательские строки снова начали хардкодиться (57 штук);
- баланс продублирован в Kotlin, C++ и текстах;
- релиз содержит два падения сборки и пустой коммит под тегом;
- локально нельзя собрать Android, поэтому цикл обратной связи — только CI.

Отсюда стратегия: **сначала дешёвые гейты и инварианты, потом новые функции**.

## 3. Этап 0 — вернуть доверие к CI (1–2 дня)

Приоритет: **P0**. Без этого остальное не имеет смысла.

1. **Защита ветки `main`.**
   - запретить прямой push;
   - обязательные проверки: `Android APK` (включая `run_host_tests.py`, `testDebugUnitTest`, `lintDebug`, `assembleRelease`) и `CodeQL`;
   - запретить merge при красном CI.
2. **Разделить workflow на джобы** `native-tests` → `lint` → `unit-tests` → `assemble`, чтобы по логу было видно, что именно упало. Сейчас всё в одном job.
3. **Артефакты:** APK, отчёт lint, отчёт тестов (`build/test-results/**`) — загружать всегда, не только при успехе.
4. **Кэш Gradle** уже есть через `gradle/actions/setup-gradle`; добавить `cache-read-only` для PR, чтобы не портить кэш ветки.
5. **Локальный паритет:** добавить в README раздел «как прогнать то же, что CI» и `tools/check.sh`, который вызывает host-тесты и (при наличии SDK) Gradle. На этой машине SDK нет — скрипт должен явно печатать, что Android-часть проверяется только в CI.
6. **Правило тега:** тег ставится только на коммит, который уже зелёный в `main`; пустые коммиты под тегом запрещены.

Критерий готовности: PR с заведомо сломанным тестом не мержится; в `main` нет красных коммитов.

## 4. Этап 1 — корректность механик (P0, 3–5 дней)

1. **Исправить F-01/F-02/F-03** по плану из `docs/mechanics-check.md` (вариант C).
2. **Ввести инварианты** и закрепить их тестами:

   - `I1`: из любого состояния, кроме `Dead`, существует действие, улучшающее голод или снимающее болезнь.
   - `I2`: `wake()` при `energy <= kForcedSleepEnergy` даёт окно бодрствования не меньше 60 с.
   - `I3`: ни одно действие не списывает энергию, если сессия отменяется.
   - `I4`: `stats_` всегда в `[0, 100]`, `weightKg` в `[1, 99]`.
   - `I5`: смерть возможна только при `hunger == 0` и только если игрок не взаимодействовал.

3. **Детерминированный фаззинг без новых зависимостей.** В `test_android_native.cpp` добавить прогон 10 000 случайных последовательностей действий с фиксированным seed и проверкой I1–I5. Это ловит целые классы ошибок порядка операций (как F-03) почти бесплатно.
4. **Единый источник баланса.** Вынести константы в `GameConstants.kt` и генерировать/сверять их с native. Минимум — тест, который парсит `VaiwuPet.cpp` и сверяет `8.0f` с `GameConstants.PlayEnergyCost`. Идеально — один JSON, из которого читают обе стороны.
5. **Убрать «оптимистичные» сообщения.** Любое сообщение об успехе должно зависеть от `result` **и** от фактического состояния после действия.

Критерий готовности: тесты из `docs/mechanics-check.md §9.3` падают на старом коде и проходят на новом; фаззинг зелёный.

## 5. Этап 2 — тестовая архитектура (P1, 5–7 дней)

Сейчас `PetViewModel` намертво связан с `NativePet` (JNI), `Application`, `AlarmManager` и сетью. Поэтому его почти нельзя тестировать на JVM.

1. **Ввести интерфейсы-порты:**

   ```kotlin
   interface PetEngine { fun startNew(...); fun tick(now: Long); fun action(a: Int): Int; fun snapshot(): PetSnapshot; ... }
   interface SettingsStore { var apiKey: String?; var speech: Boolean; ... }
   interface ReminderPort { fun schedule(at: Long, text: String): Long; fun cancelAll() }
   interface AssistantPort { fun chat(...): String; fun weather(...): String }
   ```

   `NativePet`, `SharedPreferences`, `ReminderScheduler`, `AssistantClient` становятся реализациями. `PetViewModel` превращается в обычный `ViewModel` с конструктором; `AndroidViewModel`-обёртка или фабрика собирает реальные зависимости.

2. **Fake-реализации** для тестов: `FakePetEngine` (in-memory, повторяет контракт native), `InMemorySettings`, `RecordingReminders`, `StubAssistant`. Тогда состояния «сон + болезнь», «смерть», «ошибка сети» воспроизводятся за миллисекунды.

3. **Матрица состояний как таблица.** Один параметризованный тест: `lifeState × isSick × energyBucket → ожидаемый набор доступных действий`. Это ровно та таблица, что в `mechanics-check.md §7`, и она же защищает от повторного появления F-01.

4. **Compose UI smoke-тесты** (`androidTest`, запускаются в CI на эмуляторе или через Robolectric):
   - `Sleeping + sick` → на экране есть «Разбудить» и «Дать лекарство»;
   - `Dead` → есть только «Начать заново»;
   - `Awake + sick` → есть лекарство.

5. **Правило для багфиксов.** На каждый исправленный дефект — регрессионный тест, который падает без патча. Это уже требование `AGENTS.md`; нужно проверять его на ревью.

Критерий готовности: `PetViewModel` тестируется без Android SDK и без JNI; UI-матрица покрыта.

## 6. Этап 3 — данные и приватность (P1, 3 дня)

1. **F-05, ключ API.** Перейти на `EncryptedSharedPreferences` (AndroidX Security) или обёртку над Keystore. Добавить миграцию: прочитать старый `settings.xml`, записать в зашифрованное хранилище, удалить открытое значение.
2. **Тест на бэкап.** Юнит-тест, который читает `backup_rules.xml` и `data_extraction_rules.xml` и проверяет, что `settings.xml` и `reminders.xml` исключены из cloud-backup и device-transfer. Сейчас это верно, но ничем не защищено от регресса.
3. **F-15, потеря ключа.** Отдельная кнопка «Удалить ключ»; сохранение остальных настроек не должно затирать ключ пустым полем.
4. **F-08, `resetPet()`.** Отменять напоминания, сбрасывать `_chatBusy`, чистить `settings`-ключи, если питомец удалён (по продуктовому решению — ключ можно оставить).
5. **Проверить `allowBackup`.** Либо оставить `true` с явными исключениями, либо `false`, но тогда device-transfer тоже надо осознанно решить.

## 7. Этап 4 — ассистент и уведомления (P1, 4 дня)

1. **F-04, сеть.** Во всех вызовах `AssistantClient`:
   - проверять `errorStream` на `null`;
   - ограничивать размер ответа;
   - превращать `JSONException`/`NullPointerException` в `IOException` с понятным текстом;
   - добавить тесты на 4xx/5xx/пустое тело/битый JSON через локальный `HttpServer` или подменяемый транспорт.
2. **F-09, точность.** Продуктовое решение: либо честно писать «примерно в 7:30» и оставить inexact, либо добавить `SCHEDULE_EXACT_ALARM` + `canScheduleExactAlarms()` и деградировать в inexact. Тест на `restoreAfterBoot()` с прошедшими и будущими временами.
3. **F-10, разрешения.** Запрашивать `POST_NOTIFICATIONS` при первом напоминании, с rationale; показывать статус в настройках. Если разрешения нет — говорить об этом при постановке, а не молча терять.
4. **F-11, озвучка.** Озвучивать только новое сообщение: хранить `lastSpokenId`, а не `LaunchedEffect(text, enabled)`.
5. **F-14.** Создавать канал один раз при старте приложения.

## 8. Этап 5 — i18n и консистентность UI (P2, 3 дня)

1. **F-06.** Перенести все 57 строк в `strings.xml`. Разбить по экранам: `chat_*`, `settings_*`, `games_*`, `battle_*`, `help_*`.
2. **`values-en`** как доказательство, что извлечение полное. Если строка не переводится — значит, она осталась в коде.
3. **Lint как гейт:** `HardcodedText` → `error`. Это автоматически не даст регрессу вернуться.
4. **Форматирование чисел/времени** через ресурсы (`plurals`, `String.format` с `Locale`), а не конкатенацию.
5. **F-12.** `PetSprite`: кэшировать список ассетов в `remember` на уровне приложения или вынести `assets.list` в `Dispatchers.IO`.

## 9. Этап 6 — релизная инженерия (P2, 2 дня)

1. **CHANGELOG.md** с разделами Added/Changed/Fixed по каждому тегу.
2. **Release checklist** (в `docs/release.md`):
   - [ ] `main` зелёный, host-тесты и Android-тесты прошли;
   - [ ] версия поднята в одном месте;
   - [ ] тег ставится на зелёный коммит;
   - [ ] APK собран из тега, подпись проверена;
   - [ ] смоук на устройстве: создание питомца, сон/пробуждение, лечение, игра, бой, напоминание, обновление.
3. **Версия из одного источника.** `versionName` по умолчанию должен быть осмысленным (`0.1.3`), а не `0.1.0`; лучше — из `gradle.properties`, а CI только переопределяет.
4. **F-16.** Включить `isMinifyEnabled`/`isShrinkResources` и проверить, что JNI/Compose не ломаются. Это и размер, и защита кода.
5. **F-13.** Добавить null-проверки `FindClass`/`GetMethodID` и логирование; при провале — возвращать `nullptr` и бросать Java-исключение, а не падать.
6. **Автоматизировать релиз** из тега: сборка уже есть, осталось публиковать APK и тело релиза из CHANGELOG.

## 12. Definition of Done

Задача считается выполненной, только если:

1. Есть тест (unit/host/UI), который падает без изменения и проходит с ним.
2. `python3 app/src/test/cpp/run_host_tests.py` зелёный.
3. Workflow `Android APK` зелёный (lint + unit + release).
4. Нет новых захардкоженных строк и новых магических констант.
5. Изменение не ухудшает метрики из §2.
6. Для дефекта указан воспроизводимый сценарий в описании PR.

## 13. Что не входит в план

- Новые игровые механики и контент — до стабилизации.
- Смена архитектуры на DI-фреймворк (Hilt/Koin) — избыточно на текущем размере; ручная сборка зависимостей достаточна.
- Переписывание нативного слоя — он уже host-тестируем и работает; нужны только инварианты и гистерезис.
